# Agent 工程师面试高频考点

:::观点 这套题真正在筛什么
不是在考你背了多少论文。真正想知道的是：**你有没有在生产里踩过坑、填过坑**。ReAct、Tool Calling、Checkpoint——这些词谁都说得出来；但说得清"在哪里失败、为什么失败、怎么兜底"的候选人，才是差异所在。
:::

覆盖 **编排范式、工具调用、记忆与上下文、评测与可观测性、安全、系统设计** 六个维度，按常见考察频率排列。每题附上面试官真正想听到的答案要点。

## 一、编排范式

### Q1：ReAct 是什么？它和 Chain-of-Thought 有什么区别？

**想考的**：你是否真正理解了 LLM 推理和动作能力结合的核心思路。

**好答案要点**：
- CoT 是纯内部推理（Thought），没有外部动作；ReAct 把 Thought 和 Action 交替执行，Action 的结果（Observation）反馈给下一步 Thought。
- 核心循环：`Thought → Action → Observation → Thought → ...`，直到 LLM 输出 `Final Answer`。
- 优势：可以在每步验证信息（搜索、查数据库）而不是靠记忆幻觉；动作轨迹可回溯、可 debug。
- 局限：Token 消耗大；每一步都要 LLM 调用；长任务容易跑偏。

:::提醒 常见错误
把 ReAct 描述成"只是加了个工具调用"。重点是 Thought 和 Observation 是交替可见的，让模型能根据真实反馈调整推理，不是盲目执行计划。
:::

---

### Q2：Plan-and-Execute 和 ReAct 有什么本质区别？各自适合什么场景？

**好答案要点**：

| 维度 | ReAct | Plan-and-Execute |
|---|---|---|
| 规划时机 | 每步动态决策 | 先一次性规划，再逐步执行 |
| 中途调整 | 天然支持，每步可改 | 需要专门的 replanning 节点 |
| Token 效率 | 每步都带 Thought，消耗高 | Planner 只调用一次，执行器轻量 |
| 失败处理 | 出错即时调整 | 一步出错可能影响整个计划 |
| 典型场景 | 不确定信息需要探索的任务 | 目标明确、步骤可预先分解的任务 |

生产里通常混用：高层用 Plan-and-Execute 给用户展示进度，每个子任务内部用 ReAct 处理不确定性。

### Q3：Multi-Agent 架构中，如何划分 Agent 职责？

**好答案要点**：

三种常见拓扑：
1. **Orchestrator-Worker**：主 Agent 分解任务并分配给专门 Worker，自己不做具体工作，只聚合结果。适合任务类型明确、可并行的场景。
2. **Pipeline（串行）**：每个 Agent 处理一个阶段，输出传给下一个。适合数据处理、内容生成等有明确步骤顺序的场景。
3. **Peer-to-Peer 协作**：Agent 间平等通讯、互相调用。灵活但难以 debug，生产慎用。

**职责划分原则**：
- 按能力边界而非业务功能划分（搜索 Agent、代码 Agent、验证 Agent）
- 每个 Agent 的输入输出要有明确 Schema
- 共享状态只通过约定的接口，不要全局变量
- 保持 Agent 无状态或状态可序列化，方便 Checkpoint

:::方法 面试考察点
被追问"Multi-Agent 最大的工程难点是什么"——标准答案是：**可观测性和调试**。单 Agent 失败你能看到，多 Agent 失败时你甚至不知道是哪个 Agent、哪一步出的问题。
:::

### Q4：什么是 Reflection / Reflexion？在什么场景下有用？

**好答案要点**：
- Reflexion（Shinn et al. 2023）让 Agent 在每次失败后生成语言反思（"这次为什么失败？下次怎么做"），并把反思存入记忆，影响下次尝试。
- 和普通 retry 的区别：不是重复同样的行动，而是基于失败信息修改策略。
- 适合场景：编程任务（可以运行测试判断成败）、推理任务（有标准答案校验）。
- 局限：需要可靠的成功/失败信号；自我评估容易有偏差；多次反思可能"过拟合"到错误方向。

## 二、工具调用（Tool Calling）

### Q5：Function Calling 的底层机制是什么？模型如何决定调用哪个工具？

**好答案要点**：
- Function Calling 本质是**特殊格式的输出解析**：模型在训练时被教会在合适时机输出 `{"name": "tool_name", "arguments": {...}}` 格式，而不是普通文字。
- Anthropic 和 OpenAI 都把工具描述注入 System Prompt 或专用上下文位置，让模型能"看到"有哪些工具。
- 模型通过训练学会了：何时生成工具调用（而不是文字回答）；如何根据函数签名和描述填参数。
- 运行时（Harness）解析输出，执行工具，把结果注入下一轮上下文。

**常见追问**：如果模型生成了不合法的 JSON？
→ 生产里要做结构化输出约束（JSON Schema 强制、Pydantic 验证），并设定 retry 逻辑，超过 N 次失败降级。

---

### Q6：工具设计有哪些原则？一个"好工具"应该具备什么特征？

**好答案要点**：

| 原则 | 说明 |
|---|---|
| **名称语义化** | `search_web(query)` 优于 `tool_1(input)`；模型靠名称+描述判断要不要调 |
| **参数最少化** | 每个参数都要有存在理由；可选参数要给默认值 |
| **描述即 prompt** | 工具描述是给模型看的 prompt，要说清"什么时候用、不适合什么情况" |
| **幂等优先** | 写操作要幂等（相同输入多次调用结果一样）；非幂等工具要在描述里标注 |
| **输出可解析** | 返回结构化数据，不要大段文字；模型需要能从输出中提取信息 |
| **错误信息有意义** | 失败时返回可供模型理解的错误原因，不是 HTTP 500 |

:::方法 口诀
工具描述 = 给模型的说明书。你写的描述越差，模型就越容易调错时机、填错参数。
:::

---

### Q7：什么是 MCP？它解决了什么问题？

**好答案要点**：
- MCP（Model Context Protocol，Anthropic 2024）是一个标准化协议，让 LLM 应用能以统一方式连接外部工具和数据源。
- **类比**：MCP 之于 LLM，就像 USB-C 之于设备——解决每个厂商自己搞一套适配器的问题。
- 解决的问题：在 MCP 之前，每个 Agent 框架有自己的工具定义格式（LangChain 的 Tool、OpenAI 的 Function Schema...），工具无法跨框架复用。
- MCP 核心组件：MCP Server（工具提供方）、MCP Client（Agent/Host）、标准化的 JSON-RPC 传输层。
- 生产意义：工具一次实现，任何支持 MCP 的 Agent 都能用，降低集成成本。

### Q8：Agent 工具调用的权限管理应该怎么做？

**好答案要点**：
- **最小权限原则**：每个工具只授予完成任务所需的最小权限（read-only 就不给 write）
- **双向鉴权**：Agent 调用工具时要鉴权（防越权）；工具执行结果回流时也要验证来源
- **高风险操作分级**：
  - 低风险（只读查询）：Agent 自主执行
  - 中风险（写操作、发消息）：执行前日志记录，失败可回滚
  - 高风险（删除、外部支付、权限变更）：强制 Human-in-the-Loop 确认
- **工具沙箱**：执行代码类工具必须在隔离环境（容器/MicroVM），防止宿主系统污染
- **审计日志**：每次工具调用记录：谁发起、什么工具、什么参数、什么结果、时间戳

## 三、记忆与上下文

### Q9：Agent 的四类记忆分别是什么？生产里如何实现长期记忆？

**好答案要点**：

| 类型 | 类比 | 实现 | 生命周期 |
|---|---|---|---|
| **工作记忆** | 人类当前注意力 | LLM 上下文窗口 | 单次对话 |
| **情节记忆** | 过去发生的事 | 向量数据库，按相似度检索 | 跨会话持久 |
| **语义记忆** | 概念/知识 | 知识图谱、向量库、外部文档 | 长期，更新慢 |
| **过程记忆** | 习惯/技能 | 微调模型权重、few-shot 示例库 | 随训练更新 |

**长期记忆的生产实现**：
1. 每轮对话结束时，提取关键信息写入向量库（不存原始对话，存摘要/结构化事实）
2. 对话开始时检索相关记忆，注入 System Prompt
3. 记忆有 TTL，过期信息定期清理或降权
4. 跨 session 记忆的隐私合规：区分用户是否同意记忆持久化

:::提醒 生产陷阱
记忆写入不要和对话串行——用异步队列，对话结束后再处理。检索时要用 metadata filter 确保只检索同一用户的记忆。
:::

### Q10：上下文窗口满了怎么办？有哪些压缩策略？

**好答案要点**：

| 策略 | 原理 | 适用场景 | 代价 |
|---|---|---|---|
| **滑动窗口** | 只保留最近 N 轮 | 短任务、对话 Bot | 丢失早期信息 |
| **摘要压缩** | 用 LLM 对历史对话生成摘要，替换原文 | 长对话 | 摘要质量取决于模型 |
| **重要性过滤** | 按重要性评分保留 top-k 片段 | 工具调用结果很长时 | 评分偏差可能丢关键信息 |
| **层级压缩** | 近期完整保留，远期摘要，更远丢弃 | 长任务 Agent | 实现复杂 |
| **KV Cache 复用** | 把不变的 System Prompt 部分缓存 | 高频请求、长 System Prompt | 需要 API 支持（Anthropic prompt caching）|

**实践原则**：上下文压缩要发生在"工具结果太长"时，而不是"对话历史太长"时——前者可以截断/摘要，后者需要更谨慎（可能丢失关键指令）。

## 四、评测与可观测性

### Q11：Agent 评测为什么比普通模型评测难？有哪些主流方法？

**好答案要点**：

**难点**：
- Agent 输出是轨迹（多步行动序列），不是单个答案
- 同一任务有多条有效路径（路径等价但不同）
- 中间步骤的正确性难以自动判断
- 副作用可能无法回滚（发了邮件、删了文件）

**评测维度**：

| 维度 | 衡量什么 | 方法 |
|---|---|---|
| **任务完成率** | 最终目标是否达成 | 结果比对（成功/失败二元）|
| **效率** | 完成任务用了多少步 / Token | 步骤数、Token 数 |
| **正确性** | 每步动作是否合理 | 人工标注轨迹、LLM-as-Judge |
| **鲁棒性** | 面对歧义/噪声/工具失败是否稳定 | 压力测试、故障注入 |
| **安全性** | 是否执行了不应该执行的操作 | 红队测试 |

**主流基准**：SWE-bench（代码修复）、GAIA（通用助手）、τ-bench（工具调用真实场景）

---

### Q12：LLM-as-Judge 在 Agent 评测里怎么用？有哪些坑？

**好答案要点**：

**用法**：
- 给 Judge 模型提供：任务描述 + Agent 轨迹（所有步骤）+ 评分 Rubric（1-5 分，各维度定义）
- 让 Judge 评估：每步工具调用是否合理、最终输出质量、有无幻觉

**常见坑**：
1. **Position bias**：Judge 倾向给自己先看到的答案打高分；解法：两次 A/B 互换顺序取平均
2. **Self-serving bias**：用 GPT-4 做 Judge 评测 GPT-4 的输出，评分虚高；解法：用不同厂商的模型做 Judge
3. **Verbosity bias**：Judge 偏爱更长的答案；解法：在 Rubric 里明确说明"长度不是质量"
4. **Rubric 不清晰**：Judge 对模糊标准自由发挥；解法：给 Rubric 加 few-shot 示例

:::提醒 关键原则
LLM-as-Judge 的置信度要靠人工标注校准——在 1000 条样本上和人工标注对比，计算 Cohen's Kappa 系数。低于 0.6 说明 Judge 不可靠。
:::

---

### Q13：生产 Agent 的可观测性应该监控什么？

**好答案要点**：

**三层监控**：
- **轨迹层（Trace）**：每次 Agent 调用生成一条 Trace，包含所有步骤的 Span（工具调用、LLM 调用、等待时间）。用 OpenTelemetry 采集，发送到 Langfuse / Jaeger / Datadog。
- **指标层（Metrics）**：任务完成率、P50/P95 延迟、Token 消耗量/成本、工具调用成功率、Retry 率、Fallback 率。
- **日志层（Logs）**：每个工具调用的入参和出参（脱敏后），LLM 的 Prompt 和 Response，错误栈。

**告警阈值示例**：
- 任务完成率 < 85% → 告警
- P95 延迟 > 30s → 告警
- 工具错误率 > 5% → 告警
- 单次 Token 消耗异常（> 10x 基线）→ 告警（可能无限循环）

:::方法 无限循环检测
Agent 最危险的故障是悄悄无限循环。在 Harness 层设置步骤上限（max_steps），并监控"相同工具被连续调用 3 次以上"的 Pattern。
:::

## 五、安全与风控

### Q14：什么是 Prompt 注入？在 Agent 场景下为什么更危险？

**好答案要点**：

**Prompt 注入**：攻击者在 Agent 会处理的内容里（网页、文档、用户输入）嵌入指令，试图劫持 Agent 的行为。

**Agent 场景更危险的原因**：
- Agent 有工具调用能力：成功注入后可以执行删除、发邮件、调用 API 等操作
- Agent 会访问外部内容（搜索网页、读文档）：攻击面更大，任何被 Agent 读取的内容都可能是注入载体
- 多步任务：注入可以发生在中间步骤，难以在最终输出层检测

**防御措施**：
1. **输入/输出边界标记**：用 `<document>...</document>` 等明确 XML 标签包裹外部内容，让模型区分"指令"和"数据"
2. **工具调用白名单**：不允许 Agent 执行未在明确列表里的操作
3. **输出校验**：在 Harness 层拦截最终动作，对照预期行为验证
4. **沙箱执行**：代码执行、文件操作在隔离环境里，限制可访问资源

---

### Q15：Agent 的 Human-in-the-Loop（HITL）应该怎么设计？

**好答案要点**：

**三级介入策略**：

| 级别 | 触发条件 | 介入方式 |
|---|---|---|
| **自动继续** | 低风险、高置信度操作 | 直接执行，日志记录 |
| **异步通知** | 中风险操作完成后 | 执行后推送通知，允许事后撤销 |
| **同步确认** | 高风险、不可逆操作 | 执行前等待人工确认，超时自动取消 |

**工程要点**：
- HITL 等待期间 Agent 状态要持久化（不能靠内存），避免超时后状态丢失
- 确认接口要给用户展示：将要执行什么操作、操作的影响范围、如何撤销
- 设置合理超时（如 30 分钟），超时后降级处理而不是无限等待
- HITL 节点是 Checkpoint 的天然边界点

## 六、系统设计题

### Q16：设计一个能处理 1000+ 并发的 Agent 服务，架构怎么做？

**好答案要点**：

```
用户请求 → API Gateway → Task Queue（Kafka/SQS）→ Agent Worker Pool
                                                      ↓
                                              Checkpoint Store（Redis + DB）
                                                      ↓
                                              Tool Execution Layer（沙箱）
                                                      ↓
                                              LLM Proxy（限流 + 路由）
```

**关键设计决策**：

1. **异步任务化**：Agent 任务不走同步 HTTP，而是入队列，返回 task_id；客户端轮询或 WebSocket 推送进度
2. **Stateless Worker**：Worker 本身无状态，状态全存在 Checkpoint Store（Redis for hot state，DB for persistence）
3. **LLM Proxy 层**：统一管理 API 限流、token budget、多模型路由、成本计量
4. **工具隔离**：每个 Agent 的工具调用在独立容器里执行，Worker 通过 RPC 调用，防止跨任务污染
5. **优先级队列**：高优任务（付费用户、低延迟需求）单独队列，不被长任务阻塞

**容量估算**（面试加分项）：
- 1000 并发，每任务平均 10 次 LLM 调用，每次 2s → LLM 层需要 2000 QPS
- 每任务 5 次工具调用 → 5000 次工具调用/s 峰值
- Checkpoint 写入：每步一次，1000 × 10 = 10000 次/s，需要 Redis cluster

### Q17：如何设计 Agent 的断点续跑（Checkpoint）机制？

**好答案要点**：

**核心数据模型**：
```json
{
  "task_id": "uuid",
  "step_index": 5,
  "status": "running",
  "context": {
    "messages": [...],
    "memory_refs": ["mem_id_1", "mem_id_2"]
  },
  "completed_actions": [
    {"step": 1, "tool": "search_web", "args": {...}, "result": {...}, "idempotency_key": "k1"},
    {"step": 2, "tool": "read_file", "args": {...}, "result": {...}, "idempotency_key": "k2"}
  ],
  "pending_actions": [],
  "checkpointed_at": "2026-06-23T10:00:00Z"
}
```

**续跑逻辑**：
1. 恢复时，已完成的工具调用通过 `idempotency_key` 查缓存，**不重新执行**
2. 幂等工具（查询类）出错可以重试；非幂等工具（写操作）失败要执行 Saga 补偿
3. 上下文（messages）从快照恢复，不依赖内存
4. 续跑前验证外部状态是否仍然一致（被操作的文件是否还在、API token 是否有效）

**Checkpoint 时机**：
- 每次工具调用完成后
- 等待 Human-in-the-Loop 前
- 任务被抢占/超时前（Harness 层捕获信号）

### Q18：如何评估一个 Agent 系统是否"上线就绪"（Production-Ready）？

**好答案要点**：按 Checklist 形式回答最有说服力。

**功能验证**：
- [ ] 核心任务成功率 ≥ 阈值（根据业务定义，通常 ≥ 85%）
- [ ] 覆盖了主要失败模式的降级逻辑
- [ ] 非幂等操作有幂等保护或 Saga 补偿

**安全验证**：
- [ ] Prompt 注入红队测试通过
- [ ] 所有工具调用有权限校验
- [ ] 高风险操作有 HITL 或二次确认
- [ ] 工具执行在沙箱里

**可观测性验证**：
- [ ] 全链路 Trace 可查（每步的 Prompt/Output/Tool 调用）
- [ ] 告警规则已配置（完成率、延迟、无限循环检测）
- [ ] 错误案例可以在 10 分钟内定位到具体步骤

**稳定性验证**：
- [ ] Checkpoint 可以正确恢复（演练过 N 次）
- [ ] 压测下无内存泄漏、无队列积压

## 快速复习：面试最常问的 10 个术语

| 术语 | 一句话解释 |
|---|---|
| **ReAct** | Thought + Action + Observation 交替循环，每步根据反馈调整 |
| **Reflexion** | 失败后生成语言反思存入记忆，下次修改策略，不是简单 retry |
| **MCP** | Anthropic 提出的工具/数据源连接标准协议，Agent 界的 USB-C |
| **Function Calling** | 模型学会输出结构化 JSON 触发工具，Harness 解析执行并回流结果 |
| **HITL** | Human-in-the-Loop，高风险操作前等待人工确认的机制 |
| **Checkpoint** | 每步状态快照，用于断点续跑和失败恢复 |
| **Prompt 注入** | 攻击者在 Agent 读取的内容里嵌入恶意指令劫持行为 |
| **LLM-as-Judge** | 用 LLM 代替人工打分，需用人工标注校准置信度 |
| **沙箱** | 工具执行的隔离环境（容器/MicroVM），防止跨任务污染和安全逃逸 |
| **幂等性** | 相同操作执行多次结果相同——Checkpoint 恢复时跳过已执行步骤的前提 |
