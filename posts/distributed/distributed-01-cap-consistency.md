# CAP、BASE 与一致性模型：分布式系统的理论地基

CAP 定理是分布式系统讨论里被引用最多、被误解也最多的理论。"只能选两个"是个流行但不准确的说法——现实是：**网络分区（P）是分布式系统必须接受的现实，真正的选择是在分区发生时，牺牲一致性（C）还是可用性（A）**。

---

## CAP 定理

### 三个属性的精确定义

**Consistency（一致性）**：每次读操作都能读到最新写入的值，或返回错误。这里的 C 特指**线性化（Linearizability）**——操作表现得好像在单个时间线上执行。注意：这不是 ACID 里的 C（约束不被破坏），是两个同名不同义的概念。

**Availability（可用性）**：每个请求都能收到非错误响应，尽管响应的数据可能不是最新的。注意：可用性要求不能返回错误，但允许返回旧数据。

**Partition Tolerance（分区容忍）**：即使网络发生分区（部分节点间无法通讯），系统仍能继续工作，不是整体停服。

:::提醒
CAP 里的 C（Consistency）= 线性化，不是 ACID 的 C（完整性约束）。两者同名不同义，是分布式讨论中最常见的混淆来源。遇到"一致性"这个词时，先确认说话人的语境。
:::

### 为什么 P 是必选项

在实际分布式系统中，网络分区是不可避免的。丢包、交换机故障、机房断网——这些都会发生，只是频率问题。如果不容忍分区，系统在分区时必须彻底停止服务，这在生产中不可接受。所以 **P 是必选项，真正的选择是 CP 还是 AP**。

### CP vs AP 的现实映射

| 类型 | 分区时的行为 | 典型系统 |
|------|------------|----------|
| **CP** | 拒绝写（或返回错误），保证读到的数据一致 | HBase、ZooKeeper、etcd、Consul |
| **AP** | 继续服务，不同节点可能返回不同的旧数据 | Cassandra、DynamoDB、CouchDB |

:::观点
CP 和 AP 不是非此即彼的二元选择，而是一个权衡刻度盘。Cassandra 通过调整一致性级别（ONE/QUORUM/ALL）可以在 AP 和 CP 之间动态滑动——这才是生产系统的真实状态。
:::

### CAP 的局限性

CAP 只考虑了「一致性」和「可用性」，忽略了延迟这个真实世界里同等重要的维度。PACELC 定理对此做了扩展：

```
PACELC：
  - 有 Partition 时：选 Availability vs Consistency（= CAP 的核心）
  - Else（无分区时）：选 Latency vs Consistency
```

即便没有分区，强一致（如线性化写）也会增加延迟，因为需要协调多个副本。

## 一致性模型谱系

分布式系统的一致性不是布尔值，而是一个从强到弱的谱系：

```
强 ←─────────────────────────────────────────→ 弱

线性化    顺序一致    因果一致    单调读    最终一致
(Spanner) (ZooKeeper) (DynamoDB) (MySQL从库) (Cassandra)

  └─────── 需要全局协调 ────────┘└─── 不需要协调 ───┘
  （高延迟、强保证）                （低延迟、弱保证）
```

### 线性化（Linearizability）

最强的一致性模型，也是 CAP 里 C 的定义。所有操作表现得好像在单个时间线上瞬间完成，不存在「读到旧值」的可能。

实现要求：每次写操作必须等所有副本确认后才返回，读操作必须从主节点读（或用 Quorum）。

适用场景：分布式锁、Leader 选举、金融账务。

### 顺序一致性（Sequential Consistency）

所有节点看到相同的操作顺序，但这个顺序不一定与真实时钟顺序一致。比线性化弱，但仍需要全局协调。

CPU 内存模型（x86 TSO）是顺序一致性的经典案例。

### 因果一致性（Causal Consistency）

如果操作 A 因果上先于操作 B（A 的结果影响了 B 的发生），那么所有节点都能观察到这个顺序。没有因果关系的操作可以乱序。

实现：向量时钟追踪因果关系。

适用场景：社交网络的评论/回复顺序、文档协同编辑。

### 最终一致性（Eventual Consistency）

如果停止更新，所有副本**最终**会收敛到相同值，但「最终」的时间不确定，期间读到的值可能不同。

变体：
- **读你所写（Read-your-writes）**：你写完之后能立刻读到自己写的值
- **单调读（Monotonic Reads）**：不会读到比之前更旧的值
- **单调写（Monotonic Writes）**：你的写操作按顺序执行

实际系统（如 Cassandra）通常实现某种组合变体，而非裸最终一致。

## ACID vs BASE

### ACID（传统关系数据库的承诺）

| 字母 | 名称 | 含义 |
|------|------|------|
| **A** | Atomicity | 事务要么全成功，要么全回滚，没有中间状态 |
| **C** | Consistency | 事务前后数据满足完整性约束（外键、唯一性等） |
| **I** | Isolation | 并发事务之间互不干扰，有不同隔离级别 |
| **D** | Durability | 已提交的事务持久化，宕机后不丢失 |

ACID 的 I（隔离性）有四个级别，隔离越强性能越低：

```
读未提交（Read Uncommitted）  →  脏读风险
读已提交（Read Committed）    →  不可重复读风险
可重复读（Repeatable Read）   →  幻读风险（MySQL 默认）
串行化（Serializable）        →  无并发问题，性能最低
```

### BASE（分布式系统的务实选择）

| 字母 | 名称 | 含义 |
|------|------|------|
| **BA** | Basically Available | 基本可用，允许部分降级（延迟增大、功能受限） |
| **S** | Soft state | 状态不需要强一致，允许中间不一致状态存在 |
| **E** | Eventually consistent | 最终一致，不是永远不一致 |

:::方法
选择 ACID 还是 BASE 的判断标准：
- 金融账务、库存扣减、支付：→ ACID（数据错了直接损失金钱）
- 社交点赞、浏览计数、购物车展示：→ BASE（轻微不一致用户无感知）
- 订单状态、物流追踪：→ 介于两者之间，用最终一致 + 补偿机制
:::

## 时间与时钟

### 为什么时钟是个大问题

不同机器的石英晶振频率略有差异，导致时钟漂移（Clock Drift）。NTP 同步后仍有 1-100ms 误差，闰秒时甚至会时钟回拨。在分布式系统里，如果两个事件的时间戳差距小于误差范围，你无法用时间戳判断谁先发生。

Last-Write-Wins（以时间戳决定写操作胜者）策略在时钟不同步时会默默丢失数据。

### 逻辑时钟（Lamport Clock）

Lamport 时钟不追踪真实时间，只追踪**事件的因果顺序**，规则：

1. 每个事件发生时，本地计数器 +1
2. 发送消息时，附带当前计数器值
3. 收到消息时，取 `max(本地值, 消息值) + 1`

```
节点 A：  1 → 2 → 3 ────────────────→ 发送(t=3) ──────→ ...
                                                           ↓
节点 B：  1 → 2 ──────────────────────────────── 收到 → max(2,3)+1=4
```

局限：能判断「A 可能发生在 B 之前」，无法判断「A 和 B 是并发的（无因果关系）」。

### 向量时钟（Vector Clock）

每个节点维护一个向量 `[n1, n2, ..., nk]`，分别记录每个节点的逻辑时间。

```python
# 3个节点 A, B, C 的向量时钟示例
A 发生事件: [1, 0, 0]
A 发消息给 B: [2, 0, 0]
B 收到消息: [2, 1, 0]  # max([0,1,0], [2,0,0]) = [2,1,0]
B 发生独立事件: [2, 2, 0]
```

判断规则：
- 向量 A ≤ 向量 B（每一维都 ≤）：A 因果先于 B
- 向量无法比较大小：两个事件**并发**，无因果关系，需要冲突解决

Dynamo 使用向量时钟检测写冲突，然后让客户端解决（Last-Write-Wins 或应用层合并）。

### Google TrueTime

Spanner 的 TrueTime API 不返回单一时间戳，而是返回 `[earliest, latest]` 时间区间，承认时钟的不确定性。提交事务前，Spanner 等待这个不确定性窗口过去（通常 1-7ms），保证当前事务的时间戳一定大于所有已提交事务的时间戳，从而实现外部一致性。代价：需要 GPS 接收器和原子钟硬件。
