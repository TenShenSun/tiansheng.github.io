# 分布式系统全景：从单机到集群的演进之路

分布式系统不是「多台服务器」那么简单——它是用一组通过网络连接、相互协作的计算机，对外表现为一个统一系统。这个定义里藏着分布式系统的全部难点：网络随时会丢包、节点随时会宕机、各节点的时钟从来不精确一致。

本文是系列总览，建立整体认知框架，并给出全系列的阅读路线图。

---

## 为什么需要分布式系统

### 单机的三道天花板

**容量天花板**：单机内存、磁盘、CPU 有物理上限，即便是当今最强的单机，也无法支撑 Google 级别的搜索索引或 Taobao 级别的商品库存。

**可用性天花板**：单点故障（SPOF）导致全服务不可用。一台机器宕机，所有用户都受影响。99.9% 的可用性意味着每年 8.7 小时停机，而互联网业务通常要求 99.99% 甚至 99.999%。

**地理天花板**：单机无法同时为北京和纽约的用户提供低延迟服务。光速决定了物理距离的延迟下限（北京到纽约约 70ms RTT），必须在多个地域部署节点。

### 分布式的本质代价：部分失败

分布式系统引入了一个单机系统从不需要处理的问题——**部分失败（Partial Failure）**。

单机程序要么在运行，要么彻底死了。分布式系统里，节点 A 认为节点 B 死了，但节点 B 只是因为网络分区还在处理请求，并且 A 不可能在有限时间内区分「B 死了」和「B 很慢」。

:::提醒
部分失败是分布式系统区别于单机系统的本质。所有分布式设计模式的复杂性，最终都可以追溯到这一点。
:::

## 三大本质挑战

### 1. 网络不可靠

网络可能：丢包、延迟、乱序、重复投递、分区。这些不是小概率事件，在大规模系统中每天都在发生。没有任何协议能绝对保证「消息一定送达」，分布式系统只能在「假设网络最终可达」的前提下设计重试、幂等、超时机制。

### 2. 节点会故障

节点故障分两类：

| 类型 | 描述 | 处理难度 |
|------|------|----------|
| **Crash-Stop** | 节点停止响应，不再发送任何消息 | 可检测，多数系统处理这个 |
| **Byzantine Fault** | 节点发送错误或矛盾的消息（宕机前乱写） | 难，需 BFT 协议，成本高 |

绝大多数分布式系统只处理 Crash-Stop 故障，Byzantine Fault 是区块链和航天系统的专项问题。

### 3. 时钟不同步

分布式系统里没有全局时钟。NTP 可以把不同机器的时钟误差控制在几毫秒内，但无法消除。这个误差在分布式系统里至关重要——如果两个事件的时间戳差距小于误差范围，你无法用时间戳判断谁先发生。

Google Spanner 用 GPS+原子钟做 TrueTime API，代价极高。大多数系统用**逻辑时钟/向量时钟**代替物理时间来推断事件顺序。

## 演进脉络

```
阶段一：垂直扩展（Scale Up）
  单机 → 更大的单机 → 触碰物理上限

阶段二：主从复制（Replication）
  写主节点 + 多个读从节点 → 读写分离
  问题：写仍然是单点

阶段三：分库分表（Sharding）
  按 user_id / 业务规则 手动分片 → 人工路由层
  问题：跨分片查询、扩容麻烦、业务侵入重

阶段四：分布式数据库 / NoSQL
  自动分片 + 共识协议 → Cassandra / HBase / Spanner
  支持水平扩展，但 CAP 约束下要选择取舍

阶段五：云原生分布式
  Kubernetes + 微服务 + Service Mesh
  计算与存储分离，弹性伸缩成为标配
```

## 核心设计维度

分布式系统的每一个设计决策都围绕三个维度展开：

**一致性（Consistency）**：多个副本的数据是否一致？写完一个节点后，其他节点立刻能读到吗？

**可用性（Availability）**：部分节点故障时，系统是否仍能响应请求？

**分区容忍（Partition Tolerance）**：网络分区（节点间通讯中断）时，系统是否仍能工作？

:::观点
CAP 定理告诉我们，网络分区（P）是分布式系统必须接受的现实，真正的选择是在分区发生时，牺牲一致性（C）还是可用性（A）。大多数系统在正常情况下可以同时保证 C 和 A，分区只是触发取舍的异常情况。
:::

这三个维度的取舍不是二元的，而是一个可调节的刻度盘：

```
强一致 ←──────────────────────────────→ 高可用
线性化     顺序一致    因果一致    最终一致
(Spanner)  (ZooKeeper) (DynamoDB) (Cassandra)
```

## 系统拓扑模型

分布式系统有几种常见的拓扑模式，它们在复制策略上有根本差异：

**主从复制（Leader-Follower）**：写操作路由到主节点，主节点同步/异步复制到从节点。强一致但主节点是写瓶颈。典型：MySQL replication、Redis Sentinel。

**多主复制（Multi-Leader）**：多个节点都接受写操作，节点间互相同步。写吞吐高但会产生写冲突，需要冲突解决策略。典型：Google Docs 的协同编辑、CouchDB。

**无主复制（Leaderless）**：客户端并发写多个节点，用 Quorum 机制保证一致性（写 W 个节点成功 + 读 R 个节点 + W+R > N）。典型：Dynamo、Cassandra、Riak。
