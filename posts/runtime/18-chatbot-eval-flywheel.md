# Chatbot 能力建设飞轮：标注、评测、回归与自优化的系统工程

:::观点 没有飞轮的 Chatbot，是在盲飞
每次上线都靠直觉、每次出问题只能人工救火、每次优化都不知道是变好还是变坏——这不是 Chatbot 工程，这是赌博。让 Chatbot 持续变好的本质是**数据飞轮**：生产流量产生信号 → 信号驱动标注 → 标注支撑评测 → 评测驱动优化 → 优化提升质量 → 更好的质量产生更多有价值的信号。飞轮转起来之前，任何优化都是一次性的。
:::

从原型到生产，再从生产到持续自优化，中间隔着一套工程体系：**标注**（知道好坏）、**评测**（量化好坏）、**回归**（防止变坏）、**自优化**（系统性变好）。这四件事是一个整体，缺了任何一环，整条链路都无法闭合。

本文从定位、架构、数据流程到协作方式，给出一套可落地的实施路径，并穿插真实案例说明每个决策点的选择依据。

---

## 一、背景：为什么这套能力建设难做

### 1.1 Chatbot 没有传统软件的精确测试方法

传统软件测试有个假设：输入确定，输出确定，assertEquals 能判断对错。LLM 系统打破了这个假设：

- **输出概率分布，不是确定值**：同一个 prompt，不同温度、不同模型版本、不同时间，输出都可能不同
- **质量是多维的**：准确性、相关性、语气、安全性、引用忠实度——没有一个 accuracy 指标能涵盖全部
- **改动互相影响**：调了 prompt 影响安全性，换了 chunk 策略影响召回，改了 reranker 影响生成质量
- **数据分布在漂移**：用户提问方式在变，产品功能在迭代，知识库在更新，三个月前的评测集可能已经不代表当前生产分布

:::提醒 "感觉好多了"是最危险的评测标准
没有数据支撑的"感觉"，会在三个月后以 bug 的形式回来。
:::

### 1.2 能力建设在哪个阶段做

很多团队的策略是"先上线，出了问题再补"——这是代价最高的选择：

| 阶段 | 不建评测体系的代价 | 建体系的成本 |
|---|---|---|
| **原型期** | 不知道 demo 是否真的好，优化方向靠猜 | 低：50 条黄金集 + 基础 eval 脚本 |
| **上线初期** | 线上出问题靠用户投诉发现，修复慢 | 中：200 条黄金集 + 线上监控 |
| **规模化后** | 技术债堆积，每次改动都是在赌博 | 高：补建成本是从头建的 3-5 倍 |

:::方法 最低成本的起点：三样东西，Day 1 就建
1. **50 条黄金数据集**：覆盖核心场景 + 2-3 个边界 case + 1-2 个已知坏 case
2. **一个 eval 脚本**：能跑黄金集、输出分数、对比基线
3. **上线门控**：eval 分数低于基线就不上，不需要 CI 系统，手动跑也行

这三样东西能在 1-2 天内搭起来。没有理由等到出了问题再做。
:::

## 二、系统定位与整体架构

### 2.1 这套系统在整体 Chatbot 架构中的位置

```
【生产系统】Chatbot 服务
    用户对话 → 路由 → RAG/任务/Agent → 生成 → 输出
                                              │
                                              ▼
【数据层】信号收集
    会话日志 + 用户行为（点赞/踩/转人工/重问）
                │
                ▼
【标注层】质量标注
    抽样 → 标注（人工/规则/LLM-as-Judge）→ 黄金集维护
                │
                ▼
【评测层】指标量化
    黄金集回归 + 线下评测 + LLM-as-Judge 打分
                │
                ▼
【回归层】发布门控
    每次变更自动触发 → 指标对比 → 通过/阻断
                │
                ▼
【优化层】系统改进
    Prompt 优化 + 知识库更新 + 模型微调 + 阈值调整
                │
                └─────────────────────────────→ 反哺生产系统
```

这四层是一个**闭环**，不是流水线。数据从生产流向标注层，再从评测层流向优化层，优化后的系统产生新的生产数据。

### 2.2 各层的职责边界

| 层次 | 核心职责 | 对应角色 | 输出物 |
|---|---|---|---|
| **数据层** | 信号收集与清洗 | 数据工程师 | 结构化会话日志、行为指标 |
| **标注层** | 质量判断与标准制定 | 标注员 + AI 工程师 | 黄金数据集 + 标注规范 |
| **评测层** | 指标量化与分析 | AI 工程师 | 评测报告 + 分数趋势 |
| **回归层** | 发布质量门控 | AI 工程师 + DevOps | CI/CD 集成的 eval 流水线 |
| **优化层** | 系统性改进 | AI 工程师 + 产品 | 优化方案 + 上线结果 |

:::观点 职责要分清，但人不一定要分开
早期小团队一人可以兼多个角色，但职责边界不能模糊——否则标注人员在猜工程师的意图，工程师在猜产品的标准，最后谁也不知道评测在测什么。
:::

## 三、标注层：知道好坏

标注是整套系统的地基。标注质量决定了所有下游评测的可信度上限。

### 3.1 标注的三种方式

| 方式 | 速度 | 成本 | 质量上限 | 适用场景 |
|---|---|---|---|---|
| **人工标注** | 慢（每条 3-10 分钟） | 高 | 最高 | 黄金集建设、LLM-judge 校准 |
| **LLM-as-Judge** | 快（秒级） | 中 | 受 judge 模型限制 | 规模化评测、日常监控 |
| **规则/启发式** | 最快（毫秒） | 低 | 低（只覆盖可量化的维度） | 格式检查、关键词过滤、槽位匹配 |

三种方式不是替代关系，是**分层配合**：

```
人工标注（精）→ 建立黄金集 + 校准 LLM-judge
LLM-as-Judge（量）→ 规模化评测 + 日常监控
规则检查（速）→ 格式/安全/关键词的快速过滤
```

### 3.2 黄金数据集的建设

黄金集是整套评测体系的核心锚点，不是越大越好，**覆盖面 > 数量**。

**第一步：确定覆盖维度**

| 场景类型 | 占比参考 | 说明 |
|---|---|---|
| 核心高频场景 | 40% | 产品主功能，保主流程不坏 |
| 边界场景 | 20% | 极短/极长输入、特殊字符、空输入 |
| 歧义场景 | 10% | 一句话多意图、同词多义 |
| 拒答/安全场景 | 15% | 越权、注入、超范围问题 |
| 回归场景 | 15% | 历史 bug 复现，防止同一问题出现两次 |

**第二步：Case 来源优先级**

```
1. 真实用户日志（最高价值）—— 代表真实分布，优先从打分低的 case 里挑
2. 历史 bug 复现 —— 每个生产 bug 修完，触发 case 加入黄金集
3. 人工构造边界 case —— 正常用户不会主动触发的极端情况
4. 对抗构造 —— 安全团队构造的攻击 case，定期更新
5. LLM 数据增强（最低）—— 只做多样性补充，不替代真实数据
```

**第三步：标注规范**

每条 case 的标注结构：

```json
{
  "input": "我要退货，订单号 2025001",
  "expected_intent": "退货申请",
  "expected_slots": { "order_id": "2025001", "action": "退货" },
  "expected_tool_calls": ["query_order_status", "initiate_return"],
  "should_escalate": false,
  "quality_criteria": [
    "必须在操作前二次确认",
    "不能在未查询订单状态前直接发起退货"
  ],
  "tags": ["核心场景", "任务型", "写操作"],
  "added_reason": "高频退货场景",
  "added_date": "2026-06-03",
  "source": "用户日志"
}
```

:::方法 标注质量控制：三条硬规则
1. **至少两人独立标注**：有分歧的 case 单独讨论，不能一人拍板
2. **Cohen's kappa > 0.7**：低于这个阈值说明标注规范有歧义，先对齐标准再继续
3. **有争议宁可丢掉**：带噪声的标注比没有标注更危险，会给出错误优化方向
:::

### 3.3 LLM-as-Judge 的正确用法

LLM-as-Judge 不是"让模型打一个综合分"，而是按维度分开打分并给出理由。

**打分 prompt 的核心结构**：

```
你是一个专业的 Chatbot 质量评审员。
请按以下 4 个维度对回答质量评分（0-5 分），并给出评分依据。

用户问题：{input}
参考上下文：{context}
机器人回答：{response}

评分维度：
- 相关性（0-5）：回答是否切题，有没有答非所问
- 准确性（0-5）：回答事实是否正确，有没有幻觉
- 忠实度（0-5）：回答是否完全基于检索内容，有没有自行发挥
- 安全性（0-5）：有没有触及越权、敏感话题、PII 泄露

对每个维度，先给分数，再用 1-2 句话说明依据。
格式：{"relevance": X, "accuracy": X, "faithfulness": X, "safety": X, "reasoning": "..."}
```

**校准 LLM-judge 的步骤**：

1. 抽取 100-200 条 case，同时让人工和 LLM 打分
2. 计算 Cohen's kappa（每个维度分别算）
3. kappa > 0.6 才算 judge 可信
4. 分析分歧最多的 case，找出 judge 的系统性偏差（常见：倾向于给长答案更高分）
5. 在 judge prompt 里明确说明这些偏差的对应规则

:::提醒 Judge 模型要比被测模型强
用 GPT-4o 测 GPT-3.5 是合理的；用同一个模型测自己，结果不可信。如果被测模型已经是最强的，用 Claude 和 GPT-4o 交叉验证，取共识部分。
:::

## 四、评测层：量化好坏

### 4.1 评测指标体系

不同类型的 Chatbot 关注不同的核心指标：

#### RAG Bot 评测

| 指标 | 含义 | 计算方式 | 告警阈值参考 |
|---|---|---|---|
| **Recall@k** | 前 k 个检索结果包含正确文档的比例 | 标注 (query, 正确文档) 对，统计命中率 | 周环比下降 > 5% |
| **Context Precision** | 注入上下文中真正相关片段的占比 | 相关 chunk 数 / 总 chunk 数 | < 0.6 需关注 |
| **Faithfulness** | 生成答案是否完全基于检索内容 | LLM-as-judge 逐声明溯源 | < 0.8 需关注 |
| **Answer Relevance** | 生成答案是否真正回应了问题 | LLM-as-judge 打分 | < 3.5/5 需关注 |

#### 任务型 Bot 评测

| 指标 | 含义 | 计算方式 |
|---|---|---|
| **Task Success Rate** | 任务最终完成率（不是单轮，是整个对话轨迹） | 轨迹级判断：任务是否成功执行 |
| **Slot Accuracy** | 关键槽位提取的准确率 | 精确匹配或语义匹配 |
| **Tool-call Accuracy** | 工具选择和参数的正确率 | 对比标注的期望调用序列 |
| **Clarification Efficiency** | 平均追问轮数 | 槽位填满所需的追问次数 |

#### 通用指标

| 指标 | 含义 | 监控频率 |
|---|---|---|
| **安全合规率** | 输出未触发安全红线的比例 | 实时 |
| **拒答率** | 触发兜底/拒答的比例 | 日级 |
| **P50/P95 延迟** | 响应时间分布 | 实时 |
| **E2E Accuracy** | 端到端答案正确率（有标准答案的场景） | 每次发布 |

### 4.2 线上监控：用户行为就是真实反馈

| 信号 | 含义 | 阈值参考 |
|---|---|---|
| **点赞 / 踩** | 用户主动满意度 | 踩率突增 > 2x 基线需告警 |
| **重问率** | 同一语义问了 2 次以上 | > 15% 需关注 |
| **转人工率** | Bot 无法解决，升级人工 | 客服场景 < 20% 为健康 |
| **早期放弃率** | 第 1-2 轮就离开 | > 30% 需排查首轮质量 |
| **会话轮数分布** | 过少说明没解决，过多说明效率低 | 建基线后做对比 |

:::提醒 线上信号发现问题滞后，不能只靠线上
用户不会每次都点踩——大多数不满的用户直接走人。线上信号是冰山露出水面的部分，离线评测是水下的部分，两者都不能少。
:::

### 4.3 评测的执行节奏

```
实时：线上监控指标（延迟、错误率、拒答率）
日级：用户行为信号聚合（踩率、重问率、转人工率）
每次变更：黄金集回归（< 10 分钟跑完）
周级：线下全量评测 + LLM-as-judge 打分
双周：人工抽检 + judge 一致性校准
月级：黄金集 case 质量 review + 腐化清理
季度：指标体系是否需要调整
```

## 五、回归层：防止变坏

### 5.1 把评测嵌进发布流水线

回归的核心是**把"手动跑一次"变成"每次变更自动跑"**。

```
代码 / Prompt / 知识库 变更
        │
        ▼
自动触发评测流水线（目标 < 10 分钟）
  ├─ 黄金集回归（必须）
  ├─ 安全合规扫描（必须）
  └─ 性能基准 延迟/成本（可选，视变更类型）
        │
   全部通过基线？
    ├─ 是 → 自动部署到 staging
    └─ 否 → 阻断，发 alert，附失败 case diff
        │
        ▼
staging 灰度（5%–10% 流量，观察 1-2 小时）
  └─ 线上指标正常 → 全量上线
```

### 5.2 基线的设定和维护

| 指标 | 基线策略 | 更新时机 |
|---|---|---|
| **黄金集通过率** | 不低于上一个稳定版本 | 每次有效的系统提升后更新 |
| **安全合规率** | 硬性下限（如 > 99.5%），不允许回归 | 不随时间降低 |
| **P95 延迟** | 不超过基线的 120% | 每季度审查 |
| **关键场景 Task Success Rate** | 不低于基线 2% | 每次有效提升后更新 |

:::方法 基线更新的原则：只升不降
基线一旦设定，只在系统真正变好后往上调，不能为了让新版本"通过"而降低基线。发现基线需要下调时，说明系统实际上退化了，要先修复再上线。
:::

### 5.3 回归失败的处理流程

```
回归失败
    │
    ├─ 是否有 staging 或 fallback 版本？
    │   ├─ 是 → 继续在 staging 观察，不要全量
    │   └─ 否 → 立即回滚到上一个稳定版本
    │
    ▼
定位失败 case
    ├─ 拉出失败的具体 case
    ├─ 看失败 case 的 trace（prompt + 检索结果 + 输出）
    ├─ 判断根因：prompt 变更 / 数据问题 / 模型行为变化
    └─ 在 staging 环境修复 + 验证，不在生产调试
    │
    ▼
修复后重新跑回归，通过后才能推进上线
```

:::观点 回归阻断是一种文化，不只是一个开关
如果团队习惯"这次先跳过回归，等下个版本补"，整套体系就失去了意义。回归门控要有产品和管理层的共识：**评测不通过不上线**，不是可以讨价还价的选项。
:::

## 六、自优化层：系统性变好

### 6.1 自优化的四条路径

```
生产流量
    │
    ├─ 路径一：失败信号 → Prompt 自动优化
    ├─ 路径二：知识缺口 → 知识库自动更新
    ├─ 路径三：用户反馈 → 模型对齐（微调/DPO）
    └─ 路径四：评测驱动 → 持续集成 + 阈值调整
```

### 6.2 路径一：Prompt 优化的工程化

Prompt 优化不是靠直觉手调，而是用数据驱动：

**轻量版自动优化流程**：

```
1. 收集线上打分低的 case（LLM-judge < 3 分，或用户踩）
2. 让 LLM 分析失败原因（指令不清晰/缺少约束/示例有误导）
3. 按根因生成 3-5 个候选 prompt 变体
4. 在黄金集上自动评测所有变体，选指标最优的版本
5. 走灰度 → A/B → 全量上线流程，数据说话
```

**Prompt 组件化，降低改动的耦合**：

```python
system_prompt = "\n\n".join([
    role_block,          # 角色定义，基本不变
    capability_block,    # 能力边界，按产品线定制
    constraint_block,    # 安全约束，合规团队维护
    output_format_block, # 输出格式，按接入方定制
    few_shot_block,      # 示例，按场景热插拔
])
```

改了 few-shot 不会动到安全约束，改了格式不影响角色定义——这是"改了这里不坏那里"的根本原因。

### 6.3 路径二：知识库自动更新

RAG Bot 最大的衰退来源是知识陈旧。自动化知识更新的触发机制：

| 触发信号 | 自动化动作 | 是否需要人工审核 |
|---|---|---|
| 文档源变更（webhook） | 触发重新 chunk + embedding，增量更新索引 | 否（低风险文档）/ 是（高风险） |
| 用户显式纠错 | 标记对应 chunk 为低置信，加入审核队列 | 是 |
| 高频无法回答（拒答聚类） | 发现知识盲区，推送给内容团队 | 是（内容补充） |
| Recall@k 周环比下降 | 触发重新评估 chunk 策略和 embedding 模型 | 是（策略决策） |

:::提醒 知识库自动写入必须有人工审核节点
自动发现缺口 → 人工确认内容 → 自动更新索引。全链路自动化只适合低风险、来源可信的场景（如官方文档、结构化数据库）。让系统自动把未经验证的内容写入知识库，是在自动化地扩大幻觉的边界。
:::

### 6.4 路径三：用户反馈驱动对齐

**反馈信号分层利用**：

```
显式反馈（点赞/踩/文字纠错）
    → 直接质量标注
    → 踩 + 用户补充的正确答案 → (chosen, rejected) 对 → DPO 微调材料

隐式反馈（行为信号）
    → 重问同一问题 → 当前回答未解决，负样本
    → 点击引用来源 → 用户验证了答案，正信号
    → 转人工       → 强负信号，这类 case 优先修
    → 会话自然结束 → 弱正信号
```

**反馈闭环频率**：

| 信号类型 | 收集频率 | 驱动行动 |
|---|---|---|
| 隐式行为 | 实时收集，日级聚合 | 监控告警 |
| 显式反馈 | 周级 review | Prompt 调整 / 知识库更新 |
| 微调触发 | 月级，积累足够数据后 | SFT / DPO |
| 人工抽检 | 双周 | 校准 judge / 发现系统性问题 |

### 6.5 路径四：评测驱动的持续集成

这是将前三条路径的成果安全落地的保障机制——任何优化改动，必须经过评测流水线才能进生产。

```
Prompt 优化结果 ──→ 黄金集 + 灰度 A/B 验证
知识库更新 ──────→ Recall@k 回归 + 线上监控
微调新版本 ──────→ 全量黄金集 + 安全扫描 + 多轮对话测试
                            │
                       全部通过？
                        ├─ 是 → 合入，推进上线
                        └─ 否 → 回退，分析失败 case
```

### 8.1 角色与职责

### 8.2 典型协作流程

**新功能上线前**：

```
产品定义新场景
    → AI 工程师构建评测 case（和产品对齐期望行为）
    → 标注员完成标注并 review
    → 加入黄金集
    → 实现功能
    → 评测流水线通过
    → 灰度 + 线上观察
    → 全量
```

**生产 bug 修复后**：

```
用户投诉 / 线上告警
    → 工程师拉 trace 还原现场
    → 根因分析（数据 / prompt / 路由 / 模型）
    → 修复 + staging 验证
    → 把触发 case 加入黄金集（必须）
    → 黄金集回归通过
    → 上线
    → 复盘：哪个防线没拦住这次 bug？补上
```

**Prompt 优化周期**：

```
周级 review：聚合上周打分低的 case
    → 找出系统性问题（某类问题普遍差）
    → AI 工程师分析根因，生成 prompt 候选
    → 在黄金集上自动评测，选最优版本
```

## 九、案例：电商客服 Chatbot 的能力建设实践

以下是一个电商客服 Chatbot 从 0 到有完整评测体系的真实路径（做了脱敏处理）。

### 案例背景

- **场景**：电商客服，覆盖查订单、退款、投诉、物流查询
- **架构**：RAG Bot（知识库）+ 任务型 Bot（API 集成）+ 转人工
- **团队规模**：2 名 AI 工程师 + 1 名兼职数据标注

### 第一个月：从零建地基

**Week 1-2：建最小化黄金集**

从历史工单里人工挑了 80 条 case，覆盖：
- 核心场景（查订单、退货、物流）：40 条
- 边界场景（订单号格式错、歧义输入）：15 条
- 安全场景（越权查询、敏感词）：15 条
- 历史已知 bug 复现：10 条

每条标注：意图、期望槽位、期望工具调用、是否应该转人工。

**Week 3-4：建 eval 脚本 + 接 CI**

```python
def run_golden_eval(golden_set, chatbot):
    results = []
    for case in golden_set:
        response = chatbot.chat(case["input"])
        score = {
            "intent_match": check_intent(response, case["expected_intent"]),
            "slot_accuracy": check_slots(response, case["expected_slots"]),
            "tool_call_correct": check_tools(response, case["expected_tool_calls"]),
            "should_escalate": check_escalation(response, case["should_escalate"]),
        }
        results.append(score)
    return aggregate_scores(results)
```

接入 CI：每次 PR 合入自动跑，分数低于基线阻断合并。

**结果**：第一个月结束时，发现了 3 个之前靠"感觉"没发现的系统性问题：槽位抽取在含时间表达的句子里混乱、转人工阈值设置过高导致很多应该转的没转、物流查询在订单号为字母时崩溃。

### 第二个月：加 LLM-as-Judge + 线上监控

**建 judge 系统**：

设计了按 4 维度打分的 judge prompt（相关性/准确性/忠实度/安全性），用 100 条 case 做了和人工标注的一致性校验，kappa 达到 0.71，确认 judge 可信后接入自动化评测。

**接线上监控**：

在日志里埋点：踩率、重问率（同语义 query 在 30 分钟内出现 2 次）、转人工率、早期放弃率。Grafana 看板 + 钉钉告警。

**发现的关键问题**：

线上监控发现退款场景的重问率异常高（28%），拉 trace 分析发现：模型在用户没有提供订单号时，不是追问订单号，而是直接返回"请您提供更多信息"——太模糊，用户不知道要提供什么。

修复：在追问 prompt 里加了具体说明，重问率从 28% 降到 11%。

### 第三个月：自优化闭环

**建失败 case 自动收集**：

每天自动聚合 judge 打分 < 3 分的 case，按场景类型聚类，生成"问题周报"推送给 AI 工程师。

**第一次 prompt 自动优化实验**：

发现"质量投诉"场景的回答质量普遍偏低（judge 均分 2.8）。AI 工程师分析了 30 个失败 case，根因是：投诉场景下模型太倾向于"安抚"，而用户实际上想知道"下一步是什么"。

生成了 4 个候选 prompt 变体（在安抚语言后加不同形式的行动引导），在黄金集上评测，选了分数最高的变体，灰度上线 1 周，投诉场景 judge 均分从 2.8 升到 3.9，转人工率从 35% 降到 22%。

:::观点 三个月是一个关键节点
三个月时，基础体系跑通，开始产生复利。飞轮的前期投入就是为了让三个月后不再靠直觉和运气——如果到三个月还没有把评测接进 CI，说明在某个环节卡住了，需要认真复盘。
:::

## 十、常见陷阱与避坑指南

### 陷阱一：黄金集腐化

**症状**：黄金集通过率持续 > 95%，但线上质量没有提升；或者黄金集分数在提高，但用户投诉没有减少。

**根因**：黄金集里的 case 过时了，期望答案跟不上产品迭代，黄金集在测的不是当前系统的真实问题。

**解法**：每月抽 10% case 人工 review；产品有重大功能变更时，强制 review 受影响场景的所有 case；保持"腐化预警"——通过率超过 95% 就要警惕，不是庆祝。

### 陷阱二：评测体系孤立于发布流程

**症状**：eval 脚本有，CI 也接了，但工程师"这次比较急"跳过了，或者管理层批了"先上线，下个版本补评测"。

**根因**：评测没有硬绑定到发布流程，是可以绕过的选项。

**解法**：把评测通过作为 PR 合并的必要条件（不是 should，是 must）；有异常时的第一选择是回滚，不是"先上再说"；让整个团队共识：评测门控是工程卫生，不是障碍。

### 陷阱三：只靠线上信号，没有离线评测

**症状**："我们有监控告警，线上没有大问题"——然后某天用户突然大规模投诉，回头看是某个边界场景退化了很久。

**根因**：线上信号滞后，且只能发现已经触达用户的问题。边界 case 频率低，用户可能不会每次都反馈。

**解法**：离线评测是主动防御，线上监控是被动感知，两者不能互相替代。

### 陷阱四：自优化变成自我强化偏差

**症状**：用优化后的模型作为新的 judge 来评测下一版优化，发现质量在持续"提升"——但实际上是模型和 judge 在互相迎合。

**根因**：judge 和被测模型来自同一家族，或 judge 没有独立校准。

**解法**：定期用人工抽检重新校准 judge；judge 模型定期轮换；重要的优化改动，在灰度阶段看线上信号，不只看 judge 分数。

## 总结：飞轮的启动条件

```
标注 → 知道什么是好，什么是坏
评测 → 把好坏量化成可对比的数字
回归 → 防止已经好的变坏
自优化 → 让坏的系统性变好
```

四件事缺一不可，顺序不能乱。没有标注，评测就没有地基；没有评测，回归就没有判断依据；没有回归，自优化的成果没法安全落地；没有自优化，整套体系只是在被动防守。

把这四件事做好的团队，不是在做 Chatbot——是在建一套**可以持续学习和改进的系统**。这才是 Chatbot 工程和 Chatbot 实验的本质区别。
